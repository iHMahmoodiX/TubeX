# Decisions

Short records. Status: Accepted / Proposed / Superseded.

### D-001 Stack: WXT + React + TypeScript, MV3, single package — Accepted 2026-10-20
Context: empty repository; need side panel, popup, full page, content script, local fonts, fast rebuilds. Choice: WXT 0.21.4 (MIT), React 19, TypeScript 5.9 strict, Vite 8. Alternatives: hand-rolled Vite config (more glue to maintain), Plasmo (heavier). Consequences: WXT conventions decide entrypoint layout; Windows build not yet verified (built and tested on Linux only).

### D-002 npm with `legacy-peer-deps` — Accepted 2026-10-20
Context: npm 10.9 crashes (`Cannot read properties of null (reading 'edgesOut')`) resolving vitest's optional peers alongside WXT. Choice: `.npmrc` `legacy-peer-deps=true`, with every needed peer (vite, react, typescript) pinned explicitly. Alternative: pnpm (adds a tool for the owner). Revisit when npm is upgraded.

### D-003 Storage: IndexedDB via `idb`, one owner module, optimistic revisions — Accepted
Records in IndexedDB (`src/storage/db.ts`), preferences in `chrome.storage.local`. Each record has `rev`; saves detect edits from another window and offer keep-mine / load-other. Reads are sanitized; corrupt rows are hidden and counted, never deleted.

### D-004 Unsaved-draft mirror in `localStorage` — Accepted
IndexedDB writes can be cut off when the side panel or browser closes during the autosave debounce. Edits are mirrored synchronously and replayed on next open (conflict UI if the stored draft changed meanwhile). Verified by the restart step in e2e.

### D-005 Page context is URL-first; DOM read-only, watch pages only — Accepted
URL parsing is pure and testable. DOM enrichment only on watch pages, only when the player's video id matches the URL (SPA stale-DOM guard), behind a settings kill switch. No injected UI in M1. Alternative (in-page launchers) deferred until a workflow needs them.

### D-006 No background service worker in M1 — Accepted
Nothing privileged or scheduled exists yet. It arrives with OAuth/API work (M2).

### D-007 Fonts: Estedad + Figtree bundled from Fontsource — Accepted
Both OFL-1.1 (licence files in the packages). ~210 KB of woff2 including Vietnamese/Latin-ext subsets that are loaded only on demand.

### D-008 Gate = TypeScript strict + unit tests + build + Chromium smoke; no linter yet — Accepted
Keeps tooling small. Add ESLint only if recurring issues appear that types/tests do not catch.

### D-009 Confirmations inline, not modal; reversible actions use Undo — Accepted
Matches the brief's consequence-based confirmation and avoids focus traps.

### D-010 Skills: vendor three small Markdown skills, not full design systems — Accepted
See `.agents/skills/SOURCES.md`. `ui-ux-pro-max` (30 MB with datasets and Python scripts) reviewed and not vendored.

### D-011 AI is provider-agnostic (OpenAI-compatible), called directly from the extension — Accepted
The owner wants AI that always works directly. One client covers Ollama (local, free), Gemini's OpenAI-compatible endpoint with the owner's own key, and any custom service (including a relay the owner may run on Supabase or Cloudflare). A TubeX-hosted relay was dropped: it would hold a shared key and add a service to operate.

### D-012 YouTube public data via the owner's API key before OAuth — Accepted
Research, competitor and page stats need only public data, so they ship now with an API key the owner creates. OAuth (own analytics, writes) stays M2. The daily unit cap and caching protect the default quota (Inferred 10,000 units).

### D-013 Bulk edit works on TubeX drafts and templates first — Accepted
The owner prioritized Bulk Find & Replace. Live video edits need OAuth and explicit write authorization; local bulk edit ships with preview, per-item opt-out, rev-checked saves and undo.

### D-014 Fixed extension ID via manifest `key`; OAuth with a Web application client and `launchWebAuthFlow` — Accepted
The redirect URI `https://cohhieggibbcifgenjclmjainpljkefh.chromiumapp.org/` must stay stable across installs, so `wxt.config.ts` carries the public key (the private key was discarded; a store listing would get its own). A Web application client works in Chrome and Edge (`getAuthToken` is Chrome-only, Inferred). TubeX will use the token response (no client secret in the extension); tokens live only in memory/session storage. The owner's project stays in Testing mode (owner plus up to 100 test users, no Google verification), unlike TubeBuddy/vidIQ, which are verified and audited for public use.

### D-015 Google sign-in, own analytics and live metadata writes with undo — Accepted
The owner sent the OAuth Client ID, uses Edge, has several Brand Account channels on one Google account, and authorized write access (`youtube.force-ssl`). Adds the `identity` permission and the optional host `https://youtubeanalytics.googleapis.com/*`. Scopes: `youtube.readonly`, `yt-analytics.readonly`, `youtube.force-ssl`. Token (implicit) flow through `launchWebAuthFlow`; interactive sign-in uses `prompt=select_account` so each Brand channel is added by signing in again; silent refresh uses `prompt=none` and checks the returned channel. Tokens live in `storage.session` only; channel list in `storage.local`. Live writes are limited to title, description and tags via `videos.update`, re-read the live snippet first and send every writable snippet field back, need preview plus explicit confirmation, run one at a time, stop on auth/quota/permission errors, and keep the last 10 batches for undo (undo only restores videos still holding what TubeX wrote). Alternatives: `getAuthToken` (Chrome only), a server-side token exchange (needs a client secret and a hosted service).

### D-016 0.4.0: owner's design language, background worker, in-page tools — Accepted
The owner asked (2026-10-20) for every buildable TubeBuddy feature, tools inside YouTube and Studio pages like TubeBuddy/vidIQ, and a professional redesign using the Spotify-inspired design brief he uploaded (DESIGN.md). Adds a background service worker (RPC for content scripts, scheduled jobs, notifications), permissions `alarms` and `notifications`, IndexedDB v3 working stores (jobs, trackers, snapshots, alerts; not in backups), and shadow-root islands on youtube.com/studio.youtube.com. Public API reads fall back to the signed-in channel's OAuth token when no API key is set. Scheduled work runs only while the browser is open (said in the UI). Studio form fields are filled only on click and saved by Studio's Save. Alternatives: a hosted scheduler (needs a server holding tokens), injecting into YouTube's own DOM without shadow roots (style clashes, fragile).

### D-017 Thumbnail impressions and CTR from the YouTube Reporting API — Accepted 2026-10-21
Context: on the owner's channel (issue #8), Click magnet failed with `400 badRequest: The query is not supported`: `videoThumbnailImpressions` / `videoThumbnailImpressionsClickRate` are not query metrics of the YouTube Analytics API v2. YouTube publishes them only as daily bulk reports of the official YouTube Reporting API (`youtubereporting.googleapis.com/v1`, channel reach report type, Inferred id `channel_reach_basic_a1` with columns `video_thumbnail_impressions`, `video_thumbnail_impressions_ctr`; ids, columns and the CTR unit are parsed defensively). Choice: TubeX no longer sends any impressions/CTR query to the Analytics API. On the owner's click ("Start collecting CTR data" in Reports → Click magnet) it requests the optional host `https://youtubereporting.googleapis.com/*` (added to `optional_host_permissions`; not requested at sign-in), lists report types, reuses or creates one reporting job, then lists the job's reports and downloads each CSV with the existing OAuth token. Scope: `yt-analytics.readonly` (already granted, D-015) covers non-monetary report types; no new scope. Report `downloadUrl`s are on the same host (Inferred); TubeX sends the token only to that origin and refuses any other download host instead of widening permissions; a cross-host redirect would surface as a "could not be reached" error with details (not verified live). Data kept: per video per day, impressions and estimated clicks (impressions × CTR, summed over country/subscriber dimensions), in the local IndexedDB `snapshots` work store (ref `reports.reach:<channelId>`, at most 400 days; not in backups, never sent anywhere), plus the job id and sync cursor in a `trackers` row. Sync runs on "Check now" and from the background tick at most every 6 hours while the browser is open; the owner can pause it. YouTube needs about 1–2 days before the first report and reports cover only days after the job was created (plus any backfill YouTube provides), which the UI says. Health uses this CTR only with at least 7 stored days in its 28-day window; otherwise CTR is left out, never zero. Alternatives: scraping Studio's Reach tab (forbidden: private endpoints), keeping the Analytics query (always fails), a server-side collector (needs a hosted service holding tokens).

### D-018 Staying signed in: silent renewal with login_hint, tokens stay in session storage; backups format 2 — Accepted
Owner report (#8, Edge, one Google account with several channels incl. a Brand Account): he had to sign in again every time. Cause (Inferred): tokens were only in `storage.session` (gone after a browser restart) and the silent `prompt=none` flow had no `login_hint`, so Google answered for the account's default identity; the channel check then refused it for the Brand channel. Fix: at sign-in TubeX reads the token's Google account id (`sub`) from the documented tokeninfo endpoint (`www.googleapis.com/oauth2/v3/tokeninfo`, already covered by the API host permission; the token's audience must be TubeX's client ID) and stores it with the channel in `storage.local` (an identifier, not a credential). Silent renewal sends `login_hint=<sub>` with `prompt=none`, a few minutes before expiry (one-shot `chrome.alarms` alarm, plus the 15-minute tick) and on the first worker start of each browser session, so tools do not meet an expired token. The channel check stays; a silent token for a channel the owner never connected is dropped. When Google needs the owner (signed out of Google, consent changed), the channel is marked "reconnect" for the session and Settings, the bulk page, error notices and in-page errors (`auth.reconnect` RPC) offer one "Reconnect <channel>" click: the interactive flow with the same `login_hint`, no chooser, no permission step. Tokens are NOT persisted to disk: renewing after a restart gives the same result without leaving bearer tokens in `storage.local`. Still no client secret, no auth-code/refresh-token flow. No new permissions or scopes. Unverified live: Google's behaviour for Brand Account `sub` hints in Edge's hidden auth window.
Backups move to format 2: an optional settings section (UI prefs, in-page switches, AI and YouTube settings, connected channels without tokens); AI keys and the YouTube API key only when the owner ticks them at export. Format 1 files migrate (any settings section in them is ignored). Records from older versions get defaults instead of being refused; only records with no id, no content or unusable identity are skipped, and the import preview says how many per collection and why.

### D-019 Find & replace on YouTube runs as a background job with uncapped undo — Accepted 2026-10-21
Owner's top priority: change text in the descriptions of about 400 old videos reliably. Choice: the workspace builds the plan (live preview, limits, quota estimate) and hands the operation plus the selected video ids to the service worker (`bulk.start` RPC); the worker re-reads each video (`videos.list`, part snippet, 1 unit), re-applies the operation to the fresh text, validates YouTube limits (skip with a reason, never truncate) and writes the full writable snippet (`videos.update`, part snippet, 50 units), one video at a time. Only the official Data API; no new permissions or scopes. State lives in the IndexedDB `snapshots` work store (refs `bulk.job`, `bulk.item:<jobId>`, control rows `bulk.ctl:<jobId>`), so a job survives worker restarts: the 15-minute tick resumes a job whose heartbeat is older than 3 minutes, and a lost write response is resolved by re-reading before retrying (idempotent: a video already holding the result is marked done). 429/5xx/`rateLimitExceeded` back off (2 s … 60 s with jitter); `quotaExceeded` or TubeX's own daily unit cap moves the job to "waiting" with a scheduler job (`bulk.continue`) at the next Pacific midnight + 10 minutes; auth or permission errors stop the job with a Reconnect action. Undo keeps the exact before-snippet of every changed video with the job (not capped like D-015's 10 batches; the owner removes jobs from history himself) and restores only videos still holding what TubeX wrote; others are listed as "edited since" with a diff and restored only after an explicit "restore anyway". One job at a time per profile. Alternatives: running the loop in the page (stops when the tab closes), Studio's own bulk edit (no find & replace, private endpoints).

### D-020 Persistent sign-in: code flow with PKCE through the owner's own sign-in server; refresh tokens encrypted at rest — Accepted 2026-10-22
Owner report on 0.5.2 (Edge, Brand Account channels, Web application client in Testing mode): after every browser restart each channel showed `interaction_required` and needed Reconnect; D-018's silent `prompt=none` + `login_hint` renewal does not work for him (Verified by his report; the exact Google/Edge cause is Inferred: the hidden auth window gets no usable Google session for the Brand identity). Choice: an optional "Sign-in server URL" in Settings. When set, interactive sign-in and Reconnect use the authorization code flow with PKCE (S256, `access_type=offline`, `prompt=consent` when TubeX holds no refresh token for that channel, `login_hint` when known, `state` checked) through `launchWebAuthFlow`; the code is exchanged by the owner's own free Supabase Edge Function (`server/supabase/functions/google-token`), which alone holds `GOOGLE_CLIENT_SECRET` (set by the owner in the Supabase dashboard), calls only `oauth2.googleapis.com/token` and `/revoke`, accepts only TubeX's extension origin and redirect URI, returns only the token fields and short error codes, stores and logs nothing. The refresh token is per channel (a Brand Account's chooser picks its own identity; the existing channel check `fetchOwnChannel` + `adopt` decides which channel it belongs to and a refresh token answering for another channel marks Reconnect). Refresh tokens are stored in `storage.local` (`googleRefresh`) encrypted with AES-GCM (channel id as authenticated data) under a non-extractable `CryptoKey` generated once and kept in its own IndexedDB database (`tubex-keys`); undecryptable entries are dropped. They are never logged, never part of backups (backups pick fields explicitly), deleted and revoked through the server (best effort) on Disconnect. Access tokens stay in `storage.session` as before. Renewal: a channel with a refresh token renews through the server with no window, also on the first worker start after a restart; `invalid_grant` deletes the refresh token and marks Reconnect; network/429/5xx are recorded and retried later; a setup error (`server_misconfigured`, wrong origin, 404) marks Reconnect with code `server`. Without a server URL, or for a channel without a refresh token, the D-018 token flow is unchanged. Settings shows per channel "Stays signed in" / "Click Reconnect once" / "Needs a click after a browser restart" and the last renewal error code; Settings and the Reconnect banner get "Reconnect all" (one permission request, then each channel's window in turn; closing a window stops the run).
Permissions: no manifest change. The server's origin is requested at runtime, from the Save click, as an exact `https://<host>/*` pattern under the existing optional `https://*/*` host permission. Honest limits: the encryption protects copies of the profile's storage and exports, not code running inside the extension; the server's origin check stops other websites, not other programs, which is acceptable because every action needs a code + PKCE verifier or a refresh token that only the owner's browser holds. In Testing mode Google expires refresh tokens after 7 days, so the owner publishes the app (In production; unverified is fine for personal use).
Alternatives: `chrome.identity.getAuthToken` (Chrome only, needs a Chrome App client; Edge is the owner's browser), a Desktop/installed-app client with its secret embedded in the extension (the secret would be public in a public repo — rejected), persisting access tokens in `storage.local` (expire within an hour; does not solve restarts), a paid or third-party auth service (against the no-paid-services rule; the Supabase free plan is the owner's own project).

### D-021 2026 YouTube quota model: searches have their own daily cap — Accepted 2026-11-18
YouTube's quota page (updated 2026-11-12, Verified via its public doc) gives `search.list` and `videos.insert` their own daily buckets of 100 calls; everything else shares 10,000 units, reset at Pacific midnight. Choice: TubeX counts searches separately (`Usage.ytSearches`, Settings "Daily search limit", default 100) and keeps a reserve of max(5, 20%) for the owner's manual research; search no longer spends shared units. Rank checks, tag ranks and keyword scores say "searches" instead of units.

### D-023 Optimize queue, A/B assistant and research records stored locally (DB v4) — Accepted 2026-11-18
New IndexedDB stores `optimize` (id `<channelId>:<videoId>`, per-channel, status/snooze/log with metric snapshots) and `experiments` (variants, contexts, handoff, results). Ideas and drafts gain an optional `research` record (keyword, topic, intent, language, dated public signals) and drafts an optional `platforms.aparat` package. Migration 4 only adds stores; old records stay valid. All new fields are optional and go through the same sanitizers as imports. No composite "score" in the queue: order is by number of independent signals, then by the fastest-to-act signal. A/B tests are run with YouTube Studio's own Test & Compare; TubeX prepares variants, previews them in context and records results the owner reads in Studio.

### D-024 Gemini coach needs channel-data consent; numbers must come from the evidence — Accepted 2026-11-18
Sending channel numbers to Gemini needs a one-time consent (`prefs.aiChannelConsentAt`), revocable in Settings. Calls run only on a click, never on navigation. The prompt includes only the queue item's evidence (no video id), and any number in the answer that is not in the evidence (other than small integers 1–10) drops the sentence. Without AI the rule-based advice shows. Ask Studio has no API: TubeX copies a prompt and opens Studio.

### D-025 Outliers show raw public facts, not a score — Accepted 2026-11-18
Outlier Lite compares a recent video's views per day with the median views per day of its own group (the channel's last 20 uploads or one search sample) and shows both numbers, the sample size and collection time with a qualitative flag (≥2× "above", ≥4× "far above"). No multiplier label, no stored derived metric beyond what the owner saves into an idea. Groups under 5 videos and videos under 2 days old are not compared. Bounded: up to 12 watched channels per run (1 + 2 units each, no searches) or one search.

### D-026 Aparat: no API use, local package and native handoff only — Accepted 2026-11-18
No official, documented Aparat API with OAuth or terms was found (docs/APARAT_FEASIBILITY.md); the community clients send the password hash in the URL or reuse cookies. Choice: TubeX never logs in to Aparat, uploads, edits or reads Aparat endpoints. It prepares a per-draft Aparat package checked against Aparat's own upload guidance (3–5 tags ≤ 23 characters, description ≤ 2000, title/category required; other limits only warnings), copies/downloads it, opens Aparat's upload page and records status and the aparat.com link. An opt-in "Aparat helpers" switch asks for `https://www.aparat.com/*` so the side panel can read the open Aparat tab's address and title for ideas; turning it off removes the permission.

### D-027 Platform-specific rewrites and the WordPress blog version — Accepted 2026-11-18
Owner: copying YouTube metadata to Aparat as-is is not useful; each platform needs its own SEO, and the same video should also become a post on his WordPress blogs. Choice: (1) the Aparat package applies Aparat's limits itself (5 tags ≤ 23 characters, description ≤ 2000) and an on-click AI rewrite targets Persian Aparat search; the source is always the YouTube draft and the owner reviews before it replaces anything. (2) A `platforms.blog` package per draft: the model returns a JSON outline (title, slug, meta, sections, FAQ, checklist, CTA text) in the owner's post style observed on his two blogs; TubeX renders WordPress block HTML itself with escaping (only `**bold**` becomes markup), embeds YouTube with a `wp:embed` block and Aparat with its iframe player in a `wp:html` block (embed URL format Inferred from common use; recheck live). The preview rebuilds allowed elements only. Publishing stays manual: copy into WordPress's code editor and the new-post screen opens; no WordPress credentials or REST writes (a later opt-in with an Application Password would need the owner's go-ahead). Blog sites are typed by the owner and remembered from earlier packages, not hard-coded.

### D-028 WordPress drafts through an Application Password — Accepted 2026-11-18
Owner asked to add the Application Password and to write articles from the video's captions. Choice: the owner enters site, username and Application Password in Settings; TubeX asks for that origin's host permission, tests `/wp-json` (with `?rest_route=` fallback) and the user's edit rights, and stores the credentials in extension local storage only (not in backups, not synced). Writes are limited to creating and updating posts with `status: draft`; an update refuses a post whose status is no longer draft. Tags may be created; categories are only matched. The featured image is the video's public i.ytimg thumbnail uploaded as media. Meta description goes to Yoast/Rank Math keys and the request retries without them if the site rejects them. Captions use the official captions.list/download (own videos, OAuth) on a click only.

### D-029 Owner-editable prompts with a fixed output contract; one-click republishing — Accepted 2026-11-18
Owner wants to edit the article/Aparat prompts like he does by hand, keep several templates (per content type and per blog), reset to the default, and do as little manual work as possible. Choice: prompts are stored per kind in `chrome.storage.local` ("republish", included in settings backups); the owner's text is sent first and TubeX always appends the JSON answer format (and Aparat's hard limits), which stay non-editable so parsing and limits never break. Template resolution: blog's own template → template assigned to the blog → chosen default → built-in. "Do it all" runs the existing steps in sequence in the open tab (no background job): captions (250 units) → article → WordPress draft (drafts only, existing D-028 rules), and Aparat package → AI rewrite applied directly (still nothing sent to Aparat). Batch runs are sequential and stoppable; the thumbnail permission is requested once from the click.
